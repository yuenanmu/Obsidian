# CookRPC 改造 TODO 与优先级路线图

> [!abstract] 这份清单要解决的问题
> 原仓库是「**每层都通了，每层都没收尾**」。本清单把审计发现的缺陷转成**可执行、可验收、可写进简历**的任务。
> 目标不是"把它跑起来"，而是"**把别人的作业变成我的作品**"。

> [!info] 怎么用这份文档
> **① 作为 TODO**：每个子项都是 `- [ ]` 复选框，直接在 Obsidian 里勾选。
> **② 作为思维导图**：层级结构是 `H1 标题 → H2 板块 → H3 模块 → 列表子项`，Mindmap / Markmap 类插件可直接渲染。
> - 思维导图中建议 **fold level 设为 2**，先只看「主线 / 副线 / 时间表 / 验收门」四个主干，再逐层展开。
> - 「目录」和「使用说明」这两块在导图里可以直接折叠掉，不影响主干阅读。
> - 所有叶子节点都是**单行**，避免导图节点过长。
> **③ 作为进度表**：每个模块的工时和优先级都写在 **H3 标题里**，导图上一眼可见。

## 使用说明与图例

**优先级图例**

| 标记 | 含义 | 判断标准 |
|---|---|---|
| **P0** | 阻断项 | 不做，后面全部做不了 |
| **P1** | 核心项 | 做了才有简历价值 |
| **P2** | 加分项 | 做了明显区分于同班同学 |
| **P3** | 整洁项 | 顺手做，不影响主线 |

**任务卡格式**：每个模块统一用四个标签描述，便于快速扫读。

- `复现`：先证明问题真的存在（这是"我发现的"而不是"我抄的"的关键）
- `修复`：改什么
- `验收`：可量化、可复跑的标准
- `产出`：能写进简历的一句话 / 留下的证据文件

> [!warning] 铁律：先写复现，再动手改
> 不要跳过 `复现`。**没有复现的修复，面试时讲不出"为什么"**，而且无法证明你真的改对了。
> 每个复现测试本身就是简历上"单元测试 / 集成测试"的经历。

### M4 A级缺陷围剿 · 30h · P1

> 主线的核心，也是**简历的主素材**。5 个缺陷全部会导致数据错误或丢失。

#### M4.1 TCP 分帧与半包重组 · 10h

- [ ] **复现**：客户端发送 1MB 请求体，跑 100 次
	- 预期现状：出现解压失败 → 服务端 `RemoveConnection` 断开连接
	- 依据：`connection.cpp:179` 用"密文≥12字节"判定收全，长度信息藏在密文内部
- [ ] **复现②**：一次 `write` 连续发出两条请求
	- 预期现状：只处理第一条，第二条被 `connection.cpp:248` 的 `read_buffer_.clear()` 静默丢弃
- [ ] **修复**：在加密**之前**加 4 字节长度前缀（或独立于加密在 TCP 层加帧头）
- [ ] **修复②**：接收侧改为「攒够长度 → 解密 → 循环抽取下一条」，不再整块 clear
- [ ] **验证**：16KB / 64KB / 1MB / 5MB 四档报文各 100 次，零失败
- [ ] **验证②**：粘包用例通过（两条请求都被处理并各自回包）

`验收`：大报文与粘包测试 100% 通过；连接不再因半包异常断开
`产出`：**"定位并修复 TCP 半包/粘包导致的连接异常断开与请求静默丢失，实现长度前缀分帧与循环抽取"** ← 全项目最值钱的一条

#### M4.2 EPOLLOUT 写回压 · 7h

- [ ] **复现**：服务端返回 5MB 响应，客户端读取前 `sleep 2s`
	- 预期现状：响应丢失，客户端超时
	- 依据：`connection.cpp:284` 遇 `EAGAIN` 直接 break，全仓库无 `EPOLLOUT`
- [ ] **修复**：实现 `Connection::SendInBuffer()`（现在只有声明没有定义）
- [ ] **修复②**：`MessageCycle` 在写未完成时注册 `EPOLLOUT`，写完用 `EPOLL_CTL_MOD` 摘掉
- [ ] **修复③**：`HandleEpollEvents` 增加可写分支
- [ ] **验证**：5MB 响应完整到达；`stress_test.sh -c 50 -r 200` 成功率 100%

`验收`：大响应 + 慢客户端场景零丢失；压测成功率 100%
`产出`：**"实现基于 EPOLLOUT 的写回压机制，解决高并发/大响应下的数据丢失"**

#### M4.3 写缓冲并发保护 · 4h

- [ ] **复现**：用 M3.4 的 TSan 构建，单连接发 100 并发请求
	- 预期现状：TSan 报 `write_buffer_` 数据竞争
	- 依据：响应在**线程池 worker** 里 `conn->Write()`，而 `write_buffer_` 无任何锁
- [ ] **修复**：给 `Connection` 的写路径加锁，或改为一写队列 + 事件循环单线程 flush
- [ ] **清理**：删掉从未使用的 `is_writing_`，或真正用起来
- [ ] **验证**：TSan 零报告；响应逐条内容正确、无交错

`验收`：TSan 干净；并发下响应不串包
`产出`：**"修复连接对象在多线程写场景下的数据竞争（ThreadSanitizer 验证）"**

#### M4.4 请求-响应配对与客户端并发 · 7h

- [ ] **复现**：客户端多线程同时 `Call()`，或去掉 `rpc_client.h:63` 的全程锁
	- 预期现状：响应错配（`sequence_id` 从不校验）
- [ ] **修复**：客户端用 `sequence_id → promise` 映射表做响应配对
- [ ] **修复②**：`AsyncCall` 改为真正的并发（不再共用一把大锁）
- [ ] **验证**：1000 次并发调用全部正确配对，内容与请求一一对应
- [ ] **验证②**：对比改造前后并发 QPS（预期大幅提升）

`验收`：并发调用零错配；QPS 相对 M2.4 基线有可量化提升
`产出`：**"重构客户端为请求-ID 配对模型，消除串行锁瓶颈，并发吞吐提升 X 倍"**

#### M4.5 请求侧长度校验 · 2h

- [ ] **复现**：构造 `message_length` 与实际不符的请求包
- [ ] **修复**：`RpcRequest::Deserialize` 补上 `RpcResponse::Deserialize:225` 已有的长度校验
- [ ] **顺带**：删掉响应里重复存储的 `sequence_id`；给 `error_code_` 加初始值
- [ ] **验证**：畸形包被拒绝且返回明确错误码，不崩溃

### M5 B级接线修正 · 12h · P1

> 这些不是"没写"，而是"写对了但接错了位置" —— 修完能直接对应训练计划的验收标准。

- [ ] **M5.1** 负载均衡接线修正 · 3h
	- 现状：`initBalancer` 只在**服务端**读配置时调用，客户端永远退化成随机
	- 修复：`rpc_client.json` 增加 `load_balance_strategy` 字段，客户端启动时真正初始化
	- 验收：客户端日志不再出现 `"Load balancer not initialized"`；切策略能观察到选路变化
	- `产出`：**"修正负载均衡策略未在客户端生效的接线缺陷"**
- [ ] **M5.2** `thread_pool.core_threads` 解析 · 1h
	- 现状：`ThreadPoolConfig` 根本没读这个字段 → 线程池以 0 个 worker 启动
	- 验收：启动后 `ls /proc/<pid>/task` 线程数与配置的 8 一致
- [ ] **M5.3** `max_connections` 截断修正 · 1h
	- 现状：`uint16_t` 把 800000 截成 13568
	- 验收：读取值与 JSON 一致（或把 JSON 改成合理值如 4096）
- [ ] **M5.4** 加权轮询真正支持权重 · 3h
	- 现状：权重硬编码为 1，等于普通轮询
	- 修复：从配置或 ZK 节点数据读取权重
	- 验收：配置 3:1 权重后，采样 1000 次比例接近 3:1
	- `产出`：**"为加权轮询实现可配置权重（原实现权重恒为 1）"**
- [ ] **M5.5** ZooKeeper watch 化 · 3h
	- 现状：`watch=0` 无监听，`global_watcher` 是空壳，每次调用同步拉一次 ZK
	- 修复：注册子节点 watcher + 本地缓存 + 变更回调
	- 验收：手动增删 ZK 节点后，客户端**立即**感知；正常调用不再产生 ZK 往返
	- `产出`：**"用 ZooKeeper Watch 替换轮询式服务发现，消除每请求一次 ZK 往返"**
- [ ] **M5.6** 日志修正 · 1h
	- 客户端补 `Logger::GetInstance().Init()`
	- CMake 定义 `SPDLOG_ACTIVE_LEVEL=SPDLOG_LEVEL_DEBUG`（否则 `LOG_DEBUG` 编译期被删）
	- 验收：`../logs/cookrpc.log` 在客户端侧也生成；DEBUG 日志可见

### M6 安全加固 · 8h · P2

> 原实现是「名为 AES 的自定义移位密码 + 硬编码主密钥」，写进简历会被问穿。修完才能写。

- [ ] **M6.1** 替换为真正的 AES-GCM · 5h
	- CMake 已链 Crypto++ 但代码从未 include，**改造成本很低**
	- 用 AES-GCM（自带完整性校验，顺带解决"篡改不报错"）
